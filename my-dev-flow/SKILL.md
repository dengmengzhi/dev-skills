# 新需求开发工作流

跨项目通用。项目专属规则不写在本技能里，而是在阶段 0 从项目自身的约定文件中读取。

## 适用边界

**走该流程**：有需求文档 / 原型 / Figma / 口述诉求的新需求或新功能，涉及新页面、新模块、跨多文件改动。

**不走该流程，直接做**：单文件改动、bugfix、纯文案或样式微调、依赖升级、无行为变化的重构。

## 阶段 0 · 摸清项目（每次必做，不可跳过）

不要凭记忆假设项目的技术栈和命令。

- 读项目约定文件：`CLAUDE.md`、`AGENTS.md`、`.cursorrules`、`README`、`CONTRIBUTING`。把其中的**硬规则**（禁止改动的目录、必须先查的 API、新增模块的多处联动清单、命名与分层约定等）逐条摘出来，写进设计文档专门一节，编码时当 checklist 用。
- 识别验证命令，来源按优先级：项目约定文件里明写的 > `package.json` scripts / `Makefile` / `pyproject.toml` / `Cargo.toml` > 通用默认。需要拿到四类：**格式化、类型检查、lint、测试**。缺失或有歧义时问用户，不要猜命令名。
- 识别架构文件：`ARCHITECTURE.md`、`docs/architecture*`、`docs/adr/`、`docs/design/` 等描述分层、模块边界、依赖方向、数据流、技术选型的文件。有则通读，把其中的架构原则摘进设计文档第 3 节，并把文件路径记进设计文档头部元信息（编码完成后要回写更新）；没有则明确记录"无架构文件"。
- 识别文档落点：优先项目已有的 `docs/` 或 `doc/`，都没有则新建 `docs/`。
- 识别测试组织方式：与源码同目录（`*.test.ts`）还是独立 `tests/` 目录，跟随项目现状。

## 阶段 1 · 明确需求

- **先要 PRD 文档地址**：Confluence / 飞书 / Notion / Jira / 本地路径都可以，原样记进设计文档头部元信息，便于日后追踪需求来源。用户没给就主动问；确实没有 PRD 时记录"无 PRD，需求来自口述对齐（YYYY-MM-DD）"，不要留空。
- 读需求/原型文档，列出需求点与交互明细。**有歧义或缺失先问，不要自行假设。**
- 无文档时：与用户口述对齐需求点，确认后同样产出设计文档。
- 遵循项目既有架构整理落地方案：拆分需求细节、梳理可复用的既有模块、落地组件/模块设计、分析对现有功能的影响点。**优先复用和扩展，而非新建平行实现。**
- 涉及视觉界面时主动询问 Figma 链接，按模块拆分并把链接挂在对应模块设计下；无 Figma 则明确记录"按项目现有 UI 规范实现"。
- 涉及接口时确认接口状态：已就绪 → 确认契约与生成方式；未就绪 → 先定好 mock 数据契约，并在文档中标注为待联调。
- 产出设计文档 `docs/<需求名>_<YYYYMMDD>.md`。文档开头先写元信息（缺项写"无"并注明原因，不留空）：

  ```
  - PRD 地址：<链接或路径>
  - Figma 地址：<总链接，分模块链接挂在第 5 节>
  - 架构文件：<路径，或"无">
  - 创建日期 / 需求负责人
  ```

  再写固定小节：
  1. 明确需求（需求点 + 交互）
  2. 需求框架图；**需求含状态流转时追加状态流转图**（订单/审批/任务状态、多态页面、带草稿与发布的内容等），用 mermaid `stateDiagram-v2` 画清状态、触发动作、流转条件、终态与非法流转，无状态流转则省略该图
  3. 项目硬规则（阶段 0 摘出的条目）
  4. 复用模块与扩展点
  5. 模块/组件设计（含各模块 Figma 链接）
  6. 影响点（受影响的既有页面/接口/公共模块）
  7. 任务清单（`- [ ]` checkbox，编码阶段逐条勾掉）
  8. 验收用例（阶段 4 逐条执行的依据）+ 需要覆盖的自动化测试点（哪些逻辑必须有测试、哪些只做手工验收）

**闸门：设计文档写完后停下，等用户确认，确认前不写任何业务代码。**

## 阶段 2 · 编码

- 动手前先跑基线（类型检查 + 测试）并记录结果。**大多数存量项目本身就有失败用例和 lint 报错，验收标准是"相比基线无新增失败"，不是绝对全绿。**
- 按任务清单逐条实现，每完成一条回写勾选（context 中断或 `/clear` 后据此续做）。
- 逐条遵守设计文档第 3 节的项目硬规则；涉及"新增某类模块需多处联动"的清单时，逐处核对，并提醒用户是否有配套的后端/配置改动。
- **方案设计遵循架构设计原理**：分层边界、依赖方向、模块职责、数据流向一律以架构文件为准；没有架构文件时以项目既有分层现状为准。确实需要偏离时先说明理由并等用户确认，不要默默绕过分层、跨层直连或反向依赖。
- **编码完成后及时更新架构文件**：本次新增或调整了模块、分层、依赖关系、对外接口、技术选型时，同步回写架构文件（补模块条目、更新架构图与依赖说明），别让架构文件与代码脱节。改动只在既有模块内部实现、不影响架构时无需回写；项目本来就没有架构文件则跳过，不主动新建。
- 用第三方库的 API 前先查实际版本的文档或类型定义，不凭记忆写。
- 抽象克制：同一逻辑出现两次以上才抽公共，否则与调用方同目录共存。
- 测试用例随功能一起写，流程见下。

### 测试用例编写

跟着任务清单走，每完成一条功能就补对应用例，不堆到最后统一补。

1. **定范围**：核心业务逻辑、纯函数与工具、状态流转与权限判断、金额/时间/分页等边界计算 → 必须写。纯展示组件、样式、胶水代码、一次性脚本 → 不写，别为覆盖率凑数。范围有分歧时问用户。
2. **摸基建**（写第一个用例前必做）：确认测试框架与运行命令（阶段 0 已识别）、文件放置位置与命名、以及**打开一个既有测试文件当模板**，照抄它的断言风格、mock 方式、fixture/工厂函数。项目完全没有测试基建时，先问用户是否引入，不擅自加依赖和配置。
3. **列用例清单**：从设计文档取——第 1 节的需求点与交互出正常路径，第 2 节的状态流转图出每条合法迁移 + 关键非法迁移，第 6 节的影响点出回归用例，再补边界值与异常分支（空数据、超长、越权、接口失败、超时）。清单先写进任务清单对应条目下，逐条勾掉。
4. **写法**：一个用例只验证一件事；用例名写清"什么条件下期望什么结果"；AAA 结构（准备-执行-断言）；只 mock 外部依赖（网络、时间、随机数、存储、第三方 SDK），不 mock 被测对象自身；断言具体值，不用 `toBeTruthy` 之类兜底断言糊过去。
5. **验证用例真的有效**：新写的用例要确认它能失败——临时改坏实现（或先写用例后写实现）看它变红，再改回来。**恒绿的用例等于没写。**
6. 编码期间只跑相关测试文件，加快反馈；全量测试留到阶段 4 与基线对比。
7. 接口未就绪的部分按 mock 契约写用例，并在设计文档标注"待联调后复测"。

## 阶段 3 · UI 还原

仅在需求含视觉界面时执行，纯逻辑/后端需求跳过。

- 功能可跑通后再开始，不在功能未完成时提前抠像素。
- 有 Figma：用 `playwright-cli` 截图，与设计稿逐屏对比微调（间距、字号、色值、空态、加载态、错误态）。
- 无 Figma：按项目现有 UI 规范自检一致性，并可基于当前实现向用户推荐更合适的交互方式。

## 阶段 4 · 质量保证

用阶段 0 识别出的真实命令，按顺序执行：

| 检查 | 通过标准 |
| --- | --- |
| 格式化 | **必须限定到本次改动的路径**，跑全仓会重排大量无关文件、污染 diff |
| 类型检查 | 无新增错误（对比阶段 2 基线） |
| lint | 无新增报错（同样优先限定路径） |
| 测试 | 无新增失败（对比阶段 2 基线） |
| 新增测试 | 设计文档第 8 节列出的测试点均已覆盖，且每条新用例都验证过能失败 |
| 验收用例 | 读设计文档第 8 节，逐条执行全部通过 |
| 影响点回归 | 读设计文档第 6 节，逐个验证未被破坏 |
| 架构文件同步 | 架构有变更时已回写架构文件；无架构文件或架构无变更则标注跳过 |

任一项未通过就修到通过，或明确告知用户"这项跳过了 + 原因"，**不要含糊带过或谎报通过**。

## 收尾

- 输出：本次改动文件清单 + 各项验证结果（含与基线的差异）+ 遗留项（待联调接口、跳过的检查、已知限制）。
- **不执行 `git add` / `git commit` / `git push`**，改完停下，由用户自行 review 后提交。
